# V4 重构假设说明

## 范围

本次仅重构 V2 导入下单链路。V3 审批、异常工单、品控暂扣、赔付审批和跨系统 Saga 明确排除，不建表、不提供页面、不纳入队列。

## 架构决策

1. 选择异步事件驱动：10,000 行解析和入库不适合绑定一次 Serverless HTTP 请求。小于 100 行、无外部依赖、需立即一致结果的简单命令仍适合同步处理。
2. 处理单元为 500 行：20 个批次能控制单次 SQL 参数和失败重试成本，同时有足够并行度。规则引擎可能转置行数，因此 Parse Worker 按实际结果校准总行数和最后批次边界。
3. Worker 容量：文件解析并发 2，批次并发 4；单批做 1 次 SKU 查询，并以集合 SQL 批量写原有运单表和错误表。Neon 使用 HTTP 驱动，不维持常驻连接池。
4. 性能推导：20 批 / 4 并发 = 5 个处理波次。若每批 P95 5 秒，批处理约 25 秒；预扫描和一次解析预算 15 秒，队列和聚合预算 10 秒，总预算 50 秒，保留 10 秒余量。最终结果必须以真实压测报告为准。
5. Outbox：任务、批次状态和待投递事件同一数据库事务写入。Dispatcher 失败指数退避；定时恢复扫描保证“DB 已提交但消息未发出”不会丢任务。
6. 幂等：解析和批次 Worker 都用条件更新原子抢占；抢占失败立即返回。`task_id + unit_id` 唯一，运单行 ID 由 `task_id + row_number` 稳定生成，外部编码由原有运单唯一索引排他保护，任务进度只在 processing → completed 的事务中累计一次。
7. 部分成功：文件级系统错误才使任务 failed。行级业务错误写入错误表，合法行继续落库，任务为 partial_success，避免 1 行错误让 9,999 行重复处理。
8. 重复上传：相同文件内容、用户确认行和规则在 10 分钟内复用原任务，避免用户重复点击制造重复导入；超过窗口允许创建新任务，但外部编码唯一索引仍阻止重复落库。
9. SKU 降级：批量查询超过 3 秒或短暂连接失败时，仅执行本地格式校验，逐行写 E009，任务 `degraded=true`，界面显示风险。新任务自动恢复正常查询；降级任务由运营导出 E009 后重新导入补校验。
10. 敏感信息：手机号只保留前三后四，地址保留前六后二；原始文件仅服务端存储，接口不返回文件内容。生产应进一步迁移到带生命周期策略的对象存储并加密。
11. 压测数据：固定 `load-sku-` 和 `LOAD_` 前缀，脚本 UPSERT 可重跑；清理脚本按前缀和文件名精确删除。已发送 Outbox 保留 7 天，Trace 和性能日志保留 30 天。
12. 告警阈值：积压超过 5,000 行橙色；队列配置缺失红色；批次重试 3 次后任务失败；processing 超过 5 分钟进入恢复流程。

## 产品与运维待确认

- 60 秒目标是单文件还是多用户并发总吞吐，峰值并发上传数是多少？
- 部分成功是否允许立即下游履约，还是需人工确认后发布？
- 降级导入是否允许进入正式订单，还是只能进入隔离区？
- 原始文件和个人信息的法定保留期、访问审计和删除要求是什么？
- QStash、Neon 的生产套餐、区域和连接上限是什么？
- 告警需接入钉钉、PagerDuty 还是企业现有平台？
